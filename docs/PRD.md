# PRD — 한붓그리기 대결 (One-Stroke Duel)

> 버전 0.3 · 2026-11-22 · 상태: 초안
> 변경: v0.2 두 기기 네트워크 대결로 재구성 · v0.3 인프라 확정 (Vercel + Node.js 게임 서버 + Supabase)

## 1. 개요

휴대폰 두 대가 **방 코드로 연결**되어, 한 명이 한붓그리기 문제를 내면 상대 휴대폰으로 즉시 전송되고, 상대가 푸는 모습이 **출제자 화면에 실시간으로 중계**되는 1:1 대결 게임.

이 문서의 핵심은 게임 규칙이 아니라 **두 기기 간 멀티플레이어 구조**(연결, 상태 동기화, 실시간 중계, 치팅 방지, 재접속)다.

### 1.1 퍼즐 규칙 (간단히)
- N×M 격자, 일부 칸은 구멍. 상·하·좌·우 인접 칸으로 선을 이어 **모든 칸을 정확히 한 번씩** 지나면 성공.
- 출제자는 **경로를 직접 그려서** 출제 → 지나간 칸이 문제가 됨 → 풀 수 없는 문제는 구조적으로 불가능.

### 1.2 목표
| 목표 | 지표 |
|---|---|
| 친구 폰과 빠르게 연결 | 방 만들기 → 상대 입장까지 15초 이내 |
| 상대의 풀이가 "살아있는 것처럼" 보임 | 상대 입력 → 내 화면 반영 p95 200ms 이하 |
| 정답 유출·결과 조작 불가 | 풀이 완료 전 정답 경로가 도전자 기기에 전달되지 않음 |
| 네트워크 끊김에 강함 | 30초 이내 끊김은 자동 복구, 게임 이어짐 |

### 1.3 비목표
- 랜덤 매칭, 계정, 랭킹 (방 코드로 아는 사람끼리만)
- 3인 이상 방
- 네이티브 앱 (모바일 웹으로 충분)

## 2. 사용자 경험 흐름

```
A 폰                                   B 폰
──────                                 ──────
[방 만들기] → 방 코드 "4827" + QR
                                       [코드 입력 or QR/링크] → 입장
양쪽: "상대 연결됨 ●" → 둘 다 [준비]
── 라운드 1 ─────────────────────────────────────────
A: 출제 화면 (경로 그리기)             B: "A가 문제를 만드는 중… (칸 12개)" 대기
A: [출제 완료]  ───────────────────▶  B: 문제 도착, 3·2·1 카운트다운 후 풀이 시작
A: B의 선이 실시간으로 그려지는 걸 관전  B: 풀이 (타이머 60초)
```

### 2.1 "쌈뽕 포인트" (네트워크라서 가능한 연출)
- **실시간 관전**: 출제자는 도전자가 헤매고, 막히고, 되돌아가는 걸 그대로 봄
- **출제 중 긴장감**: 도전자는 출제자가 그리는 칸 수만 실시간으로 봄 (모양은 비공개)
- **이모지 리액션**: 관전 중 출제자가 😏🔥😱 를 보내면 도전자 화면에 떠오름
- **동시 카운트다운**: 두 폰에서 동시에 3·2·1 (서버 시각 기준)
- **연결 상태 표시**: 상대 핑(ms)과 연결 아이콘 (●초록 / ●노랑 / ●빨강)

## 3. 네트워크 아키텍처

### 3.1 방식 비교

| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **A. WebSocket 권위 서버 (Node.js)** | 구조 단순, 서버가 판정 → 치팅 방지, 재접속 쉬움 | 서버 운영 필요 | ✅ **채택** |
| B. WebRTC P2P (데이터 채널) | 지연 최소, 서버 비용 ↓ | 시그널링 서버 여전히 필요, 모바일 망 NAT로 연결 실패(TURN 필요), 정답이 상대 기기로 가야 해서 치팅 가능 | ❌ |
| C. Firebase/Supabase Realtime | 서버 코드 거의 없음 | 판정 로직을 클라이언트가 해야 함(조작 가능), 학습 가치 ↓, 벤더 종속 | △ 대안 |
| D. Cloudflare Durable Objects | 방 = 객체 1개라 구조가 딱 맞음, 서버 관리 불필요 | 플랫폼 학습 필요 | △ 확장 시 이전 후보 |

**결정: A. 클라이언트 ↔ 서버 ↔ 클라이언트 (Star 구조), 서버가 게임 상태의 유일한 진실(Single Source of Truth).**
턴제 + 칸 단위 입력이라 대역폭·지연 요구가 낮아 P2P의 이점이 작고, "정답을 상대에게 숨긴다"는 요구 때문에 판정자가 반드시 제3자(서버)여야 한다.

### 3.2 전체 구성 (Vercel + Supabase + Node.js 게임 서버)

> **제약**: Vercel 서버리스 함수는 요청이 끝나면 종료되므로 **WebSocket 연결을 유지할 수 없다.**
> → 실시간 게임 서버(Node.js)는 상시 실행되는 호스트에 따로 띄우고, Vercel·Supabase는 각자 잘하는 역할만 맡는다.

```
                     ┌──────────────── Vercel ────────────────┐
  폰 A / 폰 B  ──https──▶ 클라이언트 (Next.js 또는 정적 HTML)   │
      │               │  /api/* : 전적 조회 등 일반 API (선택)  │
      │               └────────────────────────────────────────┘
      │ wss://game.<도메인>
      ▼
┌─────────────── Railway (또는 Fly.io) ───────────────┐        ┌──────── Supabase ────────┐
│  Game Server: Node.js 20 + ws                       │        │ Postgres                 │
│   RoomManager → Room "4827" (상태·정답·타이머, 메모리)│──────▶│  matches, rounds (전적)  │
│   매치 종료 시 결과 저장 (service_role 키)            │        │ Auth (선택: 익명/카카오) │
└─────────────────────────────────────────────────────┘        └──────────────────────────┘
```

| 구성 요소 | 역할 | 비고 |
|---|---|---|
| **Vercel** | 클라이언트 호스팅, (선택) 전적 조회 API | 기존 사용 중 |
| **Node.js 게임 서버** | WebSocket, 방·상태 머신·검증·판정·타이머 (권위 서버) | Railway 권장 (항상 켜짐, 슬립 없음, 월 $5 내외). Render 무료 플랜은 15분 무활동 시 슬립 → 첫 접속 수십 초 지연이라 비권장 |
| **Supabase** | 매치 결과·전적 영구 저장, (선택) 로그인 | 실시간 진행 데이터는 저장하지 않음 (지연·쓰기 비용) |

- 진행 중인 방 상태는 **게임 서버 메모리**에만 둔다 (빠르고 단순). 서버 재시작 시 진행 중 방은 소멸 — 취미 규모에선 허용.
- 클라이언트는 `NEXT_PUBLIC_GAME_SERVER_URL` 환경변수로 게임 서버 주소를 받음.
- 게임 서버 CORS/Origin 검사: Vercel 도메인(+ 로컬)에서 온 WebSocket만 허용.
- (선택) Supabase Auth를 쓰면 클라이언트가 `access_token`을 `join_room`에 실어 보내고, 게임 서버가 Supabase JWT 시크릿으로 검증 → 전적을 유저에 귀속.

**검토했지만 채택하지 않은 안: Vercel 함수 + Supabase Realtime만 사용**
이동마다 `POST /api/move`(Vercel 함수) → DB 기록 → Realtime으로 양쪽에 전파. 새 호스트가 필요 없지만, 입력 1회당 HTTP + DB 쓰기 + Realtime 전파를 거쳐 지연이 커지고(콜드 스타트 포함 수백 ms), 시간 초과 판정을 위한 서버 타이머가 없어 pg_cron이나 지연 판정으로 우회해야 한다. 실시간 관전이 핵심인 이 게임엔 부적합.

#### Supabase 테이블 (전적)

```sql
create table matches (
  id uuid primary key default gen_random_uuid(),
  room_code text not null,
  player_a text not null, player_b text not null,      -- 닉네임 (Auth 쓰면 user_id 추가)
  score_a int not null,  score_b int not null,
  winner text,
  created_at timestamptz default now()
);
create table rounds (
  id bigserial primary key,
  match_id uuid references matches on delete cascade,
  round int not null, setter text not null, solver text not null,
  rows int not null, cols int not null,
  cells text not null,          -- 활성 칸 비트열
  solution int[] not null,      -- 출제자 경로 (매치 종료 후에만 저장되므로 공개 OK)
  result text not null,         -- solved | timeout | gaveup | left
  time_ms int, resets int
);
-- RLS: 읽기는 누구나(또는 본인), 쓰기는 게임 서버(service_role)만
```

### 3.3 방(Room) 상태 머신 — 서버가 관리

```
           join(2명)        둘 다 ready
 WAITING ───────────▶ LOBBY ───────────▶ SETTING ──submit_puzzle──▶ COUNTDOWN
    ▲                   ▲                   ▲                          │ 3초
    │                   │ rematch           │ 다음 라운드              ▼
 (상대 퇴장)        MATCH_END ◀── 마지막 ── ROUND_RESULT ◀── 성공/시간초과/포기 ── SOLVING
```

- 모든 상태 전이는 **서버에서만** 일어남. 클라이언트는 "요청"만 보내고 서버가 `state` 이벤트로 확정.
- 각 상태에서 허용되지 않은 메시지는 서버가 `error`로 거절 (예: SOLVING 중 출제자가 `move` 전송).

### 3.4 메시지 프로토콜 (JSON over WebSocket)

공통 형식: `{ "t": "<type>", ...payload }`. 클라이언트 → 서버 메시지에는 `seq`(증가 번호)를 붙여 응답·거절 매칭.

**클라이언트 → 서버**

| type | payload | 설명 |
|---|---|---|
| `create_room` | `{ name, settings }` | 방 생성. 응답으로 방 코드 + 세션 토큰 |
| `join_room` | `{ code, name }` | 방 입장 |
| `resume` | `{ token }` | 재접속 (세션 토큰으로 자리 복구) |
| `ready` | `{}` | 준비 완료 |
| `draft` | `{ count }` | 출제 중 칸 수 (모양은 안 보냄) |
| `submit_puzzle` | `{ rows, cols, path:number[], revealStart }` | 출제 완료. 서버가 경로 유효성 검사 |
| `move` | `{ cell }` | 풀이 중 한 칸 전진 (또는 직전 칸이면 되돌리기) |
| `reset` | `{}` | 처음부터 |
| `give_up` | `{}` | 포기 |
| `emote` | `{ e }` | 이모지 리액션 (초당 2회 제한) |
| `rematch` | `{}` | 다시하기 |
| `ping` | `{ ct }` | 클라이언트 시각 (시계 보정용) |

**서버 → 클라이언트**

| type | payload | 받는 사람 |
|---|---|---|
| `room` | `{ code, token, you, players }` | 본인 |
| `state` | `{ phase, round, setter, solver, scores, deadline? }` | 양쪽 |
| `draft` | `{ count }` | 도전자 |
| `puzzle` | `{ rows, cols, cells, start? }` — **정답 경로 제외** | 양쪽 |
| `path` | `{ path:number[], v }` | 양쪽 (도전자에겐 확정, 출제자에겐 중계) |
| `round_result` | `{ result, timeMs, resets, points, solution }` — 이때 정답 공개 | 양쪽 |
| `opponent` | `{ status: "online"/"away"/"left", ping }` | 상대 |
| `emote` | `{ e }` | 상대 |
| `snapshot` | 현재 방 전체 상태 | 재접속한 본인 |
| `error` | `{ seq, code, msg }` | 본인 |
| `pong` | `{ ct, st }` | 본인 |

### 3.5 핵심 시퀀스: 출제 → 풀이 → 실시간 중계

```
폰 A (출제)                    서버                         폰 B (도전)
   │ submit_puzzle(path)        │                               │
   │ ─────────────────────────▶ │ 경로 검증 (인접·중복·최소 칸) │
   │                            │ solution 저장 (메모리에만)     │
   │ ◀── state(COUNTDOWN, deadline=T+3s) ──▶                    │
   │ ◀────────── puzzle(cells, start?) ───────────────────────▶ │  ← 정답 없음
   │                            │                               │
   │                            │ T+3s: state(SOLVING, deadline)│
   │                            │ ◀────────── move(cell=7) ──── │ 로컬에 먼저 그림(예측)
   │                            │ 검증: 인접? 미방문? 활성 칸?   │
   │ ◀── path([..,7], v=12) ─── │ ─── path([..,7], v=12) ─────▶ │ 확정 (불일치 시 서버값으로 교정)
   │   (관전 화면 갱신)          │                               │
   │                            │ 모든 칸 방문 → 성공 판정       │
   │ ◀──── round_result(solved, 23.4s, solution) ────────────▶ │
```

**원칙**
1. **정답은 서버 밖으로 나가지 않는다** — 라운드 종료 시점에만 `round_result`로 공개.
2. **판정은 서버가 한다** — 클라이언트가 "다 풀었어요"라고 보내는 메시지는 존재하지 않음. 서버가 `move` 누적 결과로 직접 판정.
3. **클라이언트 예측 + 서버 교정** — 내 입력은 즉시 화면에 그리고(지연 0 체감), 서버의 `path`(버전 `v`)가 오면 그 값으로 덮어씀.
4. **중계는 전체 경로 전송** — 칸 수가 최대 49개라 매번 전체 path를 보내도 수백 바이트. 증분(delta)보다 단순하고 패킷 유실·순서 문제에 강함.

### 3.6 시간 동기화
- 타이머의 주인은 서버. `state`에 **절대 시각 `deadline`(서버 기준 ms)** 을 담아 보냄.
- 클라이언트는 `ping/pong`으로 시계 오차 계산: `offset = st - (ct + rtt/2)`, 최근 5회 중앙값 사용.
- 화면 타이머 = `deadline - (Date.now() + offset)`. 두 폰의 카운트다운이 거의 동시에 끝남.
- 시간 초과 판정도 서버 `setTimeout`이 수행 → 클라이언트 시계를 조작해도 무의미.
- 풀이 기록 시간 = 서버가 SOLVING 진입 ~ 마지막 `move` 수신 시각. (지연 보정: 해당 플레이어 평균 RTT/2 차감)

### 3.7 연결 끊김 / 재접속
- 방 생성·입장 시 서버가 **세션 토큰** 발급 → `localStorage` 저장 (+ URL 해시 백업).
- 클라이언트: `close` 감지 시 지수 백오프(0.5s, 1s, 2s, 4s… 최대 5s)로 재연결 → `resume(token)` → 서버가 `snapshot` 전송 → 화면 복원.
- 서버: 플레이어 소켓 끊김 시 상대에게 `opponent: away` 알림, **30초 유예**.
  - 도전자가 SOLVING 중 끊기면 타이머 **일시정지**, 복귀 시 재개 (모바일 망 전환·화면 꺼짐 고려).
  - 30초 내 미복귀 → 해당 라운드 상대 승리 처리, 이후 추가 30초 내 미복귀 시 매치 종료.
- 하트비트: 서버가 15초마다 WebSocket ping, 응답 없으면 끊김 처리 (좀비 연결 정리).
- 모바일 백그라운드: `visibilitychange`로 복귀 감지 시 즉시 연결 상태 점검.

### 3.8 방 코드 / 입장
- 4자리 숫자 코드 (동시 방 수가 적은 취미 규모 기준). 만료: 비어있는 방은 5분 후 삭제.
- 입장 방법 3가지: 코드 입력 / QR 스캔 (A 화면에 QR 표시) / 공유 링크 `https://…/#room=4827` (Web Share API로 카톡 전송).
- 방 정원 2명. 3번째 입장은 `error: ROOM_FULL`.

### 3.9 보안 / 남용 방지
- `wss://` (TLS) 필수
- 메시지 크기 제한 4KB, 소켓당 초당 메시지 30개 제한 (초과 시 경고 후 끊기)
- 모든 입력값 서버 검증 (칸 인덱스 범위, 격자 크기 4~7, 이름 길이 12자)
- 방 코드 무차별 대입: IP당 `join_room` 실패 분당 10회 제한
- 개인정보 저장 없음 (이름은 방 메모리에만, 방 삭제 시 소멸)

### 3.10 확장 (필요해질 때)
| 상황 | 대응 |
|---|---|
| 서버 재시작 시 방 소멸이 문제 | 방 상태를 Redis에 저장 |
| 동시 방 수천 개 / 다중 인스턴스 | 방 코드 → 인스턴스 라우팅, 또는 Cloudflare Durable Objects로 이전 (방 1개 = DO 1개) |
| 관전자 기능 | `role: spectator`로 입장, `path`/`draft` 이벤트만 수신 |

## 4. 게임 규칙 / 점수

- 매치 = 3라운드 (1/3/5 선택) × 역할 교대 → 각자 3번 출제, 3번 풀이
- 판 크기 4×4 ~ 7×7 (방 설정), 출제 최소 칸 수 = 전체의 50%
- 출제 제한 시간 60초 (초과 시 그 시점까지 그린 경로로 자동 출제, 최소 칸 미달이면 출제자 패널티 -50)
- 풀이 제한 시간 60초 (30/60/120 선택)

| 상황 | 도전자 | 출제자 |
|---|---|---|
| 성공 | 100 + 남은 초 × 2 − 리셋 × 5 (최소 50) | 0 |
| 실패 / 포기 / 이탈 | 0 | 100 |

동점 시 총 풀이 시간이 짧은 쪽 승리.

## 6. 비기능 요구사항
- 입력 → 상대 화면 반영 p95 200ms 이하 (같은 국가 내 LTE 기준)
- 서버 1대(256MB)로 동시 방 500개 이상
- 모바일 세로 화면 우선, 스크롤·확대 제스처 차단
- 서버 로직(검증·판정·점수)은 순수 함수로 분리해 단위 테스트
